# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

LingoLLM: a self-hosted tool for learning languages with OpenAI-compatible LLMs. The user keeps one *language profile* per language they learn (a template such as Japanese or German, a name, a note) and everything they practise (free chats, later lessons and exercises) belongs to a profile. One Java 25 web app (Vaadin Flow UI, Spring XML without Spring Boot, Hibernate + SQLite + Flyway), packaged as a single WAR. Runs in Docker (Jetty) or as a desktop app (`lingollm/src/desktop`, `DesktopLauncher`, JDK-only, never in the WAR). The developer docs in `manual/developer/*.md` are authoritative (architecture, building, testing, plugins).

LingoLLM is built on the platform of its sibling project Marginalia (`../marginalia`: users, settings, AIs and limits, resources, trash and cleanup, OSGi extensions, localization) and on the first prototype of the learning side (`../llllm`: languages, free chat). Marginalia's story features (manuscripts, lorebooks, summaries, tags, the generation pipeline, exports, templates) are deliberately **not** here; do not port them back without being asked.

## Environment
- Always check what kind of shell you have available before issuing commands. 
- The default `java` on a machine may be old (8): point `JAVA_HOME` at a JDK 25+ (`export JAVA_HOME=/usr/lib/jvm/java-26-openjdk`). Until the repository has its first commit, `git-commit-id-plugin` fails the build: add `-Dmaven.gitcommitid.skip=true` (the WAR then can't be packaged, it needs `git.properties`). `-o` works for offline builds once the dependencies are in `~/.m2`.

## Commands

All from `lingollm/` (the Maven project; needs JDK 25+ and Maven 3.9, build from a git clone with at least one commit — the build reads git info):

```sh
mvn package                  # build + tests; production WAR in target/lingollm-1.0.0.war
mvn package -DskipTests
mvn install -DskipTests      # also installs the classes JAR into ~/.m2 (required before building plugins)
mvn test -Dtest=LanguageCrudTest              # one class
mvn test -Dtest='LocalizationTest#name'       # one method
mvn test -Dtest='*CrudTest'                   # pattern
export MAVEN_OPTS="-XX:+EnableDynamicAgentLoading -Djdk.attach.allowAttachSelf=true -Duser.home=/path/to/dev-home"
mvn -DskipTests jetty:run    # dev mode at http://localhost:8080/
docker compose up --build    # from repo root; data in ./data
```

Use a separate `-Duser.home` for dev runs: data lives in `~/.lingollm` (also the desktop app's folder). Note `user.home` also moves Maven's repo; add `-Dmaven.repo.local=$HOME/.m2/repository`.

`pom.xml` in the repo root is the parent POM of the app and of any plugin: it holds the version (children inherit it; bump with `mvn versions:set -DnewVersion=X -DgenerateBackupPoms=false` in the root) and aggregates them, so `mvn package` there builds everything. The one plugin in the repository is `lingollm/plugins/gemma4toolsfix` (a module of the root POM); a plugin is a separate Maven project (OSGi bundle) built after `mvn install` of the app, then loaded in Admin → Extensions. It must be built from the same source tree as the app.

There is no lint step. First build is slow (Vaadin downloads Node.js and npm packages).

## Architecture (big picture)

- **No REST API / separate frontend.** Vaadin components live server-side and call Spring services directly. UI code is under `ui.*`, services in `domain.service(.impl)`, JPA repositories in `domain.repository`, entities in `domain.model`, all in `com.github.enerccio.lingollm`.
- **Spring wiring is explicit XML** (`src/main/resources/META-INF/spring/*.xml`, `webapp/config/`). A new service/repository needs a bean in `services-config.xml` — component scan does not pick up service impls. A new entity must be added to `webapp/config/persistence.xml` and needs a Flyway migration.
- **UI classes are created with `new`**, annotated `@Configurable`, and get `@Autowired` fields via **compile-time AspectJ weaving** (`aspectj-maven-plugin`/`ajc`). Plain javac (e.g. an IDE not set to Ajc) compiles fine but every injected field is `null` at runtime. Keep the `-parameters` and `preserveAllLocals` compiler options: extensions read method args/locals by name.
- **Transactions** come from Spring CGLIB proxies via `@CommonTx` / `@CommonTxReadOnly` / `@NoTx` — self-calls within a service are not transactional.
- **Ownership:** every entity belongs to a user (`OwnedEntity`); use `findAllForUser()` / `findForUser(uuid)` from `OwnedService`, never trust raw ids. Deletes are soft (`deleted=true`); admin Cleanup purges following `@CleanupReference`. Entities have `id` plus a stable `uuid` used in URLs/backups/exports.
- **Language profiles:** `Language` (entity, table `languages`) is one profile of a user; `Languages` (enum) is the template it was made from (flag, defaults, and the `LanguageUI` the workspace shows for it). Everything learned is a `LanguageBoundEntity` (`FreeChat`, `FreeChatMessage`): it has a `language` and its service extends `LanguageBoundServiceImpl`, which gives `findAllForUser(language)` and sets the language of a new object from the **session's profile**. That is the session-scoped bean `language` (type `Language`, defined like the `user` bean in `container-config.xml`: only a reference with id/uuid/template/name filled in); `LanguagePart` (the language selector at the top of the Learning tab) changes it. The last profile of a user is remembered in `UserSetting.lastLanguage` and a user without a profile gets the `LanguageCreationDialog` on first start. Don't confuse `domain.model.impl.Language` (profile) with `loc.Language` (language of the interface) — they live in different packages and one file rarely needs both.
- **Free chat:** `FreeChatMessage`s form a tree like Marginalia's story parts (`parent`, `parentChat`); attachments are *loose* links — the message keeps `ImageAttachment(resource uuid, caption)` JSON as an extended attribute, not a foreign key to `Resource`. There is no chat UI yet (see `TODO.md`), but the inference layer is complete and domain agnostic, ported from Marginalia: `InferenceService` lists models, tests a connection, `stream`s an answer and `infer`s a whole answer (optionally against a JSON schema or a class, `domain.service.structured`), and the model can call Java functions (`domain.service.function`, `FunctionRegistry.bind`, `@LLMFunction`/`@LLMParam`; up to `MAX_FUNCTION_ROUNDS` rounds). Every request checks the user's limit (`AILimitService.check`) and counts its tokens for the user (`UsageService.record`) on whatever thread it ends, using `ThreadCopyRequestAttributes`. There is no protocol entity: the response limit and reasoning come from the `AI`. Extensions can change the role of function results (`InferenceServices.addToolRoleResolver`).
- **Schema:** one Flyway migration `V1__initial.sql` in `src/main/resources/migration/`; Hibernate only validates (`hbm2ddl=validate`), so entity changes without a migration break startup. Add `V2__*.sql` etc. for changes; the project has no released database yet, so until the first release V1 may be edited instead.
- **New entity fields:** prefer `@ExtendedAttribute` (`domain.traits`; a `@Transient` field serialized into the `extendedContent` JSON by `ExtendableEntityListener`) over a real column. No Flyway migration needed, and it travels with backups. Use a real column only when the app must query, filter, sort, index or join on it in SQL (relations, `name`, `enabled`, `ordinal`, counts...). Changes to extended attributes are persisted only via the service's `save` (the fields are invisible to Hibernate dirty checking). `@ExtendedAttribute(inject = true, injectPrefix = "x")` on a `JsonObject` stores its keys as `x_*` attributes (`Language.languageSpecificData`).
- **Extension data:** `ExtendableEntity.attributes` is a dynamic `JsonObject` that is itself part of the extended attributes (stored as `attributes_*` keys in `extendedContent`). It differs from `@ExtendedAttribute` fields in being dynamic: extensions can't add fields to existing classes, so they keep their own data under their own key (`getAttributes().add("myplugin", ...)`) with no schema change, and it travels with backups/exports.
- **Limits of shared AIs:** the per-user settings (`AILimit`: UNLIMITED / TOKEN_LIMIT / NOT_AVAILABLE + a reset period) are the extended attribute `AI.limits`, a JSON object keyed by user uuid (`AILimits`), set only by the owning administrator through `AILimitService`. The tokens a user used in the current period are *not* in that JSON but in `period*` columns of their `Usage` (added up in SQL; the AI is saved only by its owner and parallel requests must not lose counts); the reset is lazy, by comparing `Usage.lastUsed` with `ResetStrategy.periodStart`. The session `User` bean has no uuid, load the user to get it.
- **Extensions:** OSGi (Felix) bundles loaded from `~/.lingollm/extensions` at runtime. UI classes marked `@Extendable` are instrumented by a ByteBuddy agent (`instruct` package, installed at startup) so plugins can register decorators before/after any method via `ExtensionService.registerDecorator`. On leave a decorator can replace the return value (`ExtendableMethodContext.getOriginalReturn/getCurrentReturn/setCurrentReturn`, chained in registration order), so the declared return type of an `@Extendable` method is plugin-visible too.
- **Public API of `@Extendable` classes:** every instrumented method (not a constructor, static, synthetic or bodiless) of an `@Extendable` class carries `@PublicAPI(from, returns = @APIReturn(type), parameters = {@APIParameter(name, type)}, locals = {@APILocals(name, type)})` (`domain.traits`): the argument names and types, the return type and the named object locals that plugins read through `ExtendableMethodContext`; types are erased class literals. `PublicAPISignatureTest` (ByteBuddy + local variable table) fails when a method has none or the annotation differs from the compiled class, and prints the annotation to paste. So when you add a method to an `@Extendable` class, or rename/retype/add/remove an argument, a named object local or the return type, or rename/move/remove a method, or split/merge such classes (refactors!): run `mvn test -Dtest=PublicAPISignatureTest`, update the annotation, set `from` to the current project version when a plugin can see the change, and fix the plugins that name the old class/method/variable (and the field names they read, which `@PublicAPI` doesn't cover). Never edit an annotation just to silence the test without checking the plugins. See `manual/developer/plugins/extendable.md`.
- **Extension logging:** plugins must not use `LoggerFactory` (their output would not reach the extension log); in `onExtensionLoad` they call `parentService.createLogger(bundle)` (`OsgiService`) and use the returned `org.slf4j.Logger` as usual (`log.info("x {}", y)`, trailing throwable). It writes to `<jar name>.log` in the extensions folder (rotated at 2 MB, deleted with the extension) and chains to the application log (logger `extension.<name>`), shown in Admin → Extensions → Log (`ExtensionLogDialog`). An extension can be stopped without uninstalling: `<jar name>.STOPPED` flag file next to the JAR (`OsgiService.stopExtension`/`startExtension`).
- **Localization:** UI strings are keys in the `L` enum (`loc/L.java`) with the texts in the `LocalizationBundle*` classes. Only `LocalizationBundleEN` (the default language, must be complete: the application refuses to start otherwise) exists; it is a stub with the keys the code uses, other languages come as extensions (`ExtensionHasLocalization`) or later bundles. `Localization` (`LocalizationImpl`) picks the bundle by the language in the session's `SessionPoint` (set from `UserSetting.language` when the workspace opens, changed by `LanguageSelector`), so never cache a looked-up text beyond the page/request. The `L` file and the bundle are grouped by key prefix (`LABEL_`, `ENUM_`, `ERROR_`, `MSG_`, `HELP_`, `DESC_`) under `// --- PREFIX ---` headers. Keys name the English text, not the screen, so reuse an existing key (e.g. `LABEL_CLOSE`) instead of adding a per-screen duplicate (before adding a key, grep `LocalizationBundleEN` for the same English text). Add new keys at the end of their prefix group in `L` and in every bundle — never at the end of the file. The names of the learnable languages are `ENUM_LANGUAGE_*` keys looked up with `Localization.getLanguageName(Languages)`. A key that no code uses should not exist: remove it with its text.
- **Styling:** prefer CSS classes over inline styles. Define the rule in `src/main/frontend/styles/shared-styles.css`, add its name as a constant to `CssStyles` (both together, same name) and apply it with `addClassName(s)(CssStyles.X)`; reuse an existing class (grep both files) before adding one, and use Lumo variables (`var(--lumo-...)`) in the rules. Do not write `getStyle().set(...)`, inline `style='...'` in `Html` strings or JS `node.style.setProperty(...)`. The only exception is a value computed at runtime (e.g. the combo box overlay width). Only styles used in more than one place belong there: a style used by a single plugin stays in that plugin (its own `src/main/resources/<plugin>.css` plus a constants class; the extension implements `ExtensionHasCss` and returns the CSS from `getCss`, the app's `CssRegistry` puts it into the pages and removes it on unload), never in `shared-styles.css`/`CssStyles`. Plugins may use the shared `CssStyles` classes. Markdown needs no styling call: the `vaadin-markdown` rule in the stylesheet already forces line wrapping for every `Markdown`.
- **Client-side JavaScript:** do not call `executeJs` from UI classes. Every script the main app runs in the browser is a static method of `ui.JavascriptLibrary` (element passed explicitly as `$0`, not `this`; value-returning scripts return the `PendingJavaScriptResult`). Add new scripts there and call them from the component. Extensions (plugins) keep their own scripts.

## Testing notes

Tests (`src/test/java`) boot the real Spring XML config (minus OSGi/instrumentation) on SQLite in `target/test-home/ctx-*`, with `LingoLLMTestBase` (`loginAs`, `createUser`, `createAI` helpers) and `MockLLMServer`, a fake OpenAI-compatible server programmed per test. Entity CRUD uses `OwnedCrudContract`/`ExtendableCrudContract` (see `LanguageCrudTest`, `FreeChatCrudTest`). No network or API key needed.

The full suite takes about a minute. Run it in the foreground without `-q` (`mvn test 2>&1 | tail -40`) or in the background and wait for the completion notification; check results in `target/surefire-reports/*.txt`. Never poll with an `until ... ps/pgrep` loop: it matches the Maven processes already running on the machine (and itself), never ends and burns the whole timeout. Steps that call an admin-only service (cleanup, database backups, user delete/unlock/clear password, extension install) need `loginAdmin()`, not `login()`. After removing or renaming a Flyway script run `rm -rf target/classes/migration` (or `mvn clean`) — stale scripts stay in `target/classes` and fail the context start.

## Other

- When creating new files, automatically add them to git
- When you implement a feature or fix, update the docs that describe it: user docs in `manual/user`, developer docs in `manual/developer`. Developer pages carry `verified` (commit last checked) and `covers` (code described) in their front matter; after a code change run `python3 tools/check_dev_docs.py` (`-v` names modified files) and update the pages it flags. Once a page matches the code, stamp it with `--stamp <page.md>` in a commit of its own (the stamp is a commit that already exists).
- `CHANGELOG.MD` (Keep a Changelog format) records every user- or plugin-visible change. When you implement a feature, change behavior, fix a bug, add a plugin or a Flyway migration, add an entry under `## [Unreleased]` in the matching `Added` / `Changed` / `Fixed` / `Known issues` section in the same change (mention the migration number, and API changes plugins can see). Purely internal work (tests, docs, refactors nobody can notice) needs no entry. When a release is cut, `[Unreleased]` becomes the new version heading with its date and the compare links at the bottom are updated.
- `manual/` is the source of the published manual (Retype; `retype.yml`): `manual/user`, `manual/developer`, screenshots in `manual/images`. `docs/` is its generated output — never edit or read it; after changing anything in `manual/`, run `retype build` in the root folder.
- `TODO.md` tracks planned work.
- Logging: `src/main/resources/log4j.properties` (DEBUG, dev) is replaced by `resources-release/log4j.properties` (INFO) in the packaged WAR so no chat content is logged.
- Configuration lives in `~/.lingollm` (`Configuration`): database, resources, extensions, backups. The Docker image keeps it in `/var/lingollm/.lingollm` (`./data` on the host).
